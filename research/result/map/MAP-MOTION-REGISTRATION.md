# 动作表登记序列 — 从原始数据 + 反编译提取

日期: 2026-11-10。本文回答：客户端动作表（0xBDDB10，149 项 × 0x18）的槽号顺序从哪来、
能恢复到什么程度。数据来源：原始 Character.wz（wzpy 第三方库解析）+ Ghidra 反编译登记函数。

## 方法论修正记录

1. **FSDB 不是"重排了顺序"**——用 wzpy（`.work/tools/wz-python`，region=EMS）直接解析
   原始 `Character.wz`（version 79），确认 **WZ 文件本身的节点顺序就是字母序**
   （airstrike → vampire → walk1 → …）。FSDB 忠实保留了原序。之前"FSDB 把顺序弄丢了"的判断是错的。
2. **WZ 字母序 ≠ 动作表槽序**。锚点（swingO1=5、stabO1=16、ladder=36、rope=37，来自登记
   写入地址（表项地址-基址)/0x18）与字母序（swingO1=125）不符。
   **表槽序 = 客户端登记函数的调用顺序。**

## 登记函数与序列（新发现，7/7 验证通过）

登记函数 RVA 0xA7F89（VA 0x4A7F89，50,775 字符）按固定模式调用 149 次：

```c
FUN_007a48d0(&str, <字符串号>);   // 从客户端内部字符串表按编号取动作名
FUN_00406368(...);                 // 字符串处理
FUN_004aee0b(<flag>, 0);           // 初始化表项 {entry+0=动画对象, entry+4=flag, ...}
[ebp-4] = <槽号>;                  // 槽号 = 调用序号（0..148）
FUN_004aa4ae(...);                 // 提交
```

从反编译代码按序提取全部 149 个 `(槽号, 字符串号, flag)` 三元组，结果在
`research/result/map/MOTION-REGISTRATION-SEQUENCE.csv`。

## 字符串号 → 名字：剩余的静态极限

字符串号→名字的映射在客户端**运行时字符串表**（全局 `DAT_00be2000`，经 `DAT_00afe084`
回调懒初始化）。已排除的可能性：

- ❌ 不在映像 UTF-16 字符串池（全部 105,748 个 UTF-16 串中无 swingO1/ladder/rope/sit）
- ❌ 不在映像 ASCII 字符串（扫描无命中）
- ❌ 不是 PE 资源 STRINGTABLE（MapleStory.exe 的 .rsrc 只有 BITMAP/ICON/DIALOG/MANIFEST，无 RT_STRING）
- ❌ 不在 List.wz（空）/ Base.wz（只有 zmap/smap/StandardPDD）

结论：该表由壳保护下的初始化代码在运行时解密/构建（可能与 0xBAADF00D 滚动 XOR 族
同源），来源 blob 尚未定位。**这是当前规则（静态分析）下真实的边界。**

已确认的 4 个锚点名字（853/864/882/884）来自用户早期反汇编的一级证据，不在本次推断。

## 对实现的含义

- 动作索引体系已可从 `MOTION-REGISTRATION-SEQUENCE.csv` 查询：任何反汇编里看到的
  动作号都能换成字符串号；四个锚点直接可读。
- 游戏实现不需要索引体系——直接用名字（WZ 149 个动作名清单见 MAP-DATA-SIDE-FINDINGS.md）。
- 登记序列里 swingO1 登记了 3 次（槽 5/24/28）、stabO1 两次（16/30）：表项是
  "动作角色槽"（攻击位 1/2/3），不是去重动作清单。149 槽对 149 个 WZ 节点是数量巧合，
  实际是"槽位语义 + 重复登记"。
