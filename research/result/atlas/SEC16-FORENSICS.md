## 1. 死亡字 +0x61

### 已证实的汇编证据
- **disp32 扫描（[reg+0x61] 双字位移）：0 条**。
- disp8 扫描（[reg+0x61] 字节位移）：**77 条**，其中 6 条 mov-b-W（写）、4 条 mov-d-W、7 条 cmp-imm8——但分布上：
  - 绝大多数落在 0xB0-0xDE 地址段（>0x9d8046，即**盲区/FUN_9d8046 合并区**），如 @0xba2fe3、@0xcc8afd、@0xd98f58；
  - 语料区内仅 0x4f38d2(FUN_4f2dc9)、0x60a567(FUN_60a556)、0x535941(FUN_5356ac) 等零星 dword 写。
- 动作字路径（0x93DDDF 族）里**没有以 0x61 为判据的分支**；dead 的动作字公式未在本次扫描中出现。

### 尚未证实的假设
- "+0x61 是死亡标志"本身仍是**草案侧假设**：77 条 disp8 引用无法在无类型信息下区分属于 user/move/哪个结构体；0x61 也可能是其它对象（UI/网络缓冲）的字段。
- dead 的槽位号：MOTION-TABLE-RUNTIME.csv 只提取到 18/149 名（含 alert=6），**dead 不在其中**；字符串池中 dead@0x2b9e56d 存在，但其槽位号未与表结构对齐验证。

### 缺失的运行时输入
- 需要一次进图后死亡事件的对象字段转储（user 基址 ±0x100 diff）才能把 77 条候选缩到唯一。

### 当前可实现程度
- **行为级**：可用动作字 `(旧&1)|X`、右移得槽位的一般机制实现"死亡→dead 姿势"，X 值取字符串序推算（未证实）。
- **字段级**：不可实现（+0x61 的归属未定）。建议 loom-realm 侧用自有状态位，不照抄 0x61。

## 2. R9 `[user+0x354]`

### 已证实的汇编证据（本轮完全闭合）
- **+0x354 全镜像扫描：13 条**（读 8 / push 5）——全部是**读取或传参**，无任何直接写：
  - `push [esi+0x354]; call 0x7737d0`（@0x935559）与 `push [esi+0x354]; call 0x773744`（@0x935577）= 攻击分派器把它传给两个表函数（与已破译的攻击变体表 0xBA59B8 同族）；
  - `cmp [esi+0x354], edi(0)`（@0x69494c）后**紧跟 `lea eax,[esi+0x358]`** —— +0x358 紧邻使用！
- **写入者破译**：0x416E36（Ghidra 间隙函数，直接反汇编）：
  ```
  mov ecx, 0xBDF028; call 0x416e71   ; 取 RNG 状态推进值
  mov [edi], esi                      ; [dst+0] = 值
  xor esi, 0xBAADF00D; call 0xa700f4  ; 滚动异或加密
  mov [edi+4], ebx                    ; [dst+1] = 键
  ```
  即 **{+0x354=值, +0x358=键} 加密对**（第 23 轮证明的 14 对布局之一）。
- **值来源**：0x416e71 = **xorshift/MT 型伪随机数发生器**（>>0xD、&0x7FFC0、<<0xC、>>6 异或级联 tempering），状态对象在全局 0xBDF028。
- 10 个调用者（0x109ec 等）以 `edx=目标槽` 调用，其中含 +0x354（与草案一致，且现在知道同时写 +0x358 键）。

### 结论（修正草案）
- 草案"0x416E36 把随机数写进 +0x354"**正确但不完整**：写的是 {随机数, 键} 加密对；+0x354 = **加密的随机数槽**，攻击时 `decrypt(+0x354,+0x358) % count` 选变体——与第 20 轮表级公式 `variant[rand%count]` 完全闭环。
- 武器类参数（1-9）来自攻击分派器的**另一个参数**（调用 0x77325B/0x773491 的第一参数），不是 +0x354。

### 缺失的运行时输入
- 无（本项已闭环）。

### 当前可实现程度
- **完全可实现**：`variant = table[weaponClass][rand() % table[weaponClass].count]`。

## 3. R13 比较器 `[eax+0xB4]`

### 已证实的汇编证据
- 0x666F7D（间隙函数，直接反汇编）：
  ```
  call [eax+0xB4]        ; 比较器（eax = 接口对象）
  cmp eax, ebx; jge ok   ; 失败 → COM 异常(0x80004003 经 0xa6ef01)
  lea eax,[ebp-0x68]; call 0x4029b7   ; VARIANT/BSTR 清理
  call [ecx+8]           ; Release
  call [eax+0xE0]        ; 第二个接口方法(0xE0/4=56 号)
  ```
  = 一个 **COM 排序回调**：取接口对象 → 调 +0xB4 比较 → 失败抛 COM 错。
- `[0xBE2788]`（对象来源）：**196 个函数引用**的接口全局槽；静态值为 0（运行时由 PcCreateObject 填充——第 9/15 轮 ATL 结论）。
- **候选缩小**：+0xB4 = 方法索引 45。38 个接口组中方法 45 存在的虚表 **19 张**，其中非链视图的实体候选：
  Gr2D 0x2f2cc(m45=0x1b84d)、Canvas 0x270e8(m45=0x1752c)、Canvas 0x27364(m45=0x85f0)、Shape2D 0xc0e0(m45=0x847d)、NameSpace 0x170f8(m45=0x1dc6)、0x17258(m45=0xf88b)、0x17548(m45=0x22e7)、0x18940(m45=0xab1b)、0x18a54(m45=0xc1bf)。

### 尚未证实的假设
- [0xBE2788] 持有**哪个**接口（渲染队列管理器？场景图？）——19 选 1。
- 草案"方法体不在这张映像里"**表述修正**：方法体在 **DLL 镜像**里（全部可读），不在 exe 镜像里。

### 缺失的运行时输入
- 一次进图转储读 [0xBE2788] 的 vtable 指针 → 与 19 候选比对即定唯一。

### 当前可实现程度
- **架构级可实现**：排序键 `z + 10*(layer*3000 - zM) - 1073721834` 已知；比较器语义 = 数值比较（候选方法体均可读，共性是 int 比较）。
- **精确复刻**：需要运行时定接口后读 m45 方法体（一次转储即闭合）。

## 4. R14 镜头

### 已证实的汇编证据（含对草案的重大修正）
- **虚表 0xB0CB70 = 移动对象虚表**！首 8 项：{0x9d356b, 0x9bc622, 0x9d3548, 0x9bf1fa, **0x9be703**(=第 23 轮物理主循环), 0x9d3cca, 0x9d3de6, 0x9bc4cc}——位置钟与物理积分同对象。
- 草案"+0x58 和 +0x110 方法体不在映像里"**错误**：+0x24→0x9d3fe1、+0x58→0x9c0ec0、+0x110→0x9bc401 **全部 < 0x9d8046，在镜像内**——只是被 Ghidra 合并进巨型函数 FUN_9069bf（0x9069bf 起始），故草案当时"找不到"。
- **0x9BCCFB 破译**（间隙函数直接反汇编）= 移动对象重置/初始化：
  ```
  rep movsd：+0x20..+0x80 槽组整体拷贝（0x60 字节 = 24 个加密槽中的 24×4）
  eax = [Physics(0xBDD498) + 0xAC]; [ebx+0x190] = eax   ← move+0x190 的写入者！
  经 [ebx+0x14] 对象的 vtbl+0xC 调用后：push 0x1E        ← 步进参数 0x1E 在此出现
  ```
  即 **+0x190 = [Physics+0xAC]**（物理对象字段，运行时由 Physics.img 装填），0x1E 是步进节拍常量。
- 镜头跟随：全镜像扫描**未找到**把 user 坐标写入视口/镜头的指令（在 0x9d8046 前区域）；盲区 7 处 +0x3BC cmp 均与镜头无关。

### 尚未证实的假设
- 0x9C0EC0（+0x58）与 0x9BC401（+0x110）的方法体**已可读**（在镜像内），本轮未及全文精读——镜头更新是否在这两者之中（含经接口间接）待读证。
- "位置钟周期 0x5A（表 0xB0C870 累加比较）与步进 0x1E 的换算关系"仍是草案推断。

### 缺失的运行时输入
- 运行时 [0xBDF54C] 场景对象的视口字段观测（验证镜头是否中心跟随 + dead zone 是否存在）。

### 当前可实现程度
- 节拍可实现：`step 输入 = 0x1E`、累加对比 0x5A 已证。
- 镜头策略可实现为"视口含角色"（第 4.2 节既有契约）；**原版精确跟随方式未证实**——不要宣称复刻，如实标注为实现决策。

## 5. `[user+0x3BC]`

### 已证实的汇编证据
- **全镜像 26 条引用**：
  - **写入 11 处**：9 处 `mov [reg+0x3BC], 0x1388`（=5000）@0x935526/0x95d870/0x96ba59/0x977cdc/0x97a1ad/0x98e48e/0x98e51c/0x990e48 + 2 处非立即数 mov-w @0x7857b8/0x78e709（FUN_76f4f8 表处理器内 = 条件清零路径候选）；
  - **读取 8 处**：cmp @0x504501/0x5401f9/0x70e6fe/0x955227/0x97a7c2 + mov-r @0x629899/0x6298d8/0x957041；
  - **盲区 7 处 cmp**（0xa0e07c/0xa12a31/0xa1849c/0xa1aac7/0xa2d8aa/0xa2fdeb/0xa31b2f——全读）。
- 写入场景：0x935526 在**攻击分派入口**（紧邻 0x451b00 调用与 [esi+0x348] 读取）；0x977cdc 在一次 vtbl+0x10 调用后；0x96ba59 附近另有 `+0x3E8`(1000) 加法。
- **递减指令：全镜像（含盲区）未找到** `sub/dec [reg+0x3BC]`。
- FUN_6292f5（读点 0x629899）= 外观构建函数（皮肤/脸/发型调用链），不是递减者。

### 尚未证实的假设
- "0x1388(5000) 之后递减到 0 切回 stand1"的**递减机制未证实**。两种可能且都无法排除：
  1. 通用计时器数组经**计算位移**遍历（固定位移扫描天然不可见）；
  2. 5000 是帧数/毫数，由 +0x58/+0x110 类节拍方法内部以读-减-写完成（该方法体在镜像内未精读）。
- FUN_76f4f8 的两处非立即写是否为清零路径：待读证。

### 缺失的运行时输入
- 进图后对 +0x3BC 做周期采样（5000 → 单调减？步长？）一次即可判定递减来源。

### 当前可实现程度
- **行为级可实现**：`alertTimer = 5000`（攻击/受击等事件触发），`>0 显示 alert 帧，每拍减 dt，到 0 回 stand1`——与 R5 槽位切换公式（`(旧&1)|8`→槽4 / `|4`→槽2）组合即得完整 stand1↔alert 机制。
- **精确递减来源**未证实，按上述等价行为实现并如实标注。
