## 未解决的缺口（按优先级）

### 1. Swim 标志连接 (field+0x150 → global +0x150)

**问题**: 地图加载把 `swim` 写到 `field+0x150`，但运行时读的是 `[0xBDF54C]+0x150`。两者之间的复制指令未找到。

**已尝试**:
- 全量 52K 函数搜索 DAT_00bdf54c + 0x150: 无直接连接
- Ghidra 反编译代码搜索: 无匹配

**下一步**:
- 检查地图加载函数（可能是一个巨大函数的内部）
- 在运行时设断点观察 [0xBDF54C] 的值变化
- 检查 Delegate 对象的虚表方法是否内部传播这个值

### 2. Swim 动画名

**问题**: swim==1 时播什么身体动作不知道。动作名表中没有 "swim"。

**已确认**:
- 动作表在 0xBDDB10, 每条 0x18 字节
- 有 fly, jump, ladder, rope, sit, prone
- 没有 swim

**下一步**:
- 搜索 0x95A31E 路径中的动作号分配（可能是 10 或 2）
- 检查动作表是否有未命名的槽位

### 3. 攻击 swing/stab 选择

**问题**: 普攻时选择挥砍(swing)还是突刺(stab)的逻辑在 57KB 攻击分派器的深处。

**已知**:
- swingO1 在动作表索引 5, stabO1 在索引 0x10
- 攻击函数 0x55C5B2 (Ghidra RVA) 有 57,191 字符反编译代码
- 动作表确实被引用 (`DAT_00bddb10 + index * 0x18`)

**下一步**:
- 在 57KB 函数中做分支追踪（从入口到动作选择点）
- 检查武器类型 → 动作选择的映射表
- 用服务端源码的 `getWeaponType()` 交叉参考

### 4. 同图传送坐标写入

**问题**: 传送门传送后人物坐标 (+0x20/+0x38) 的本地写入未找到。

**已知**:
- 坐标通过加密调用链写入: `FUN_006131F4(value, target)`
- 位置在移动对象上, +0x20 = x, +0x38 = y
- 绳索函数 0x5D7D5A 有先例: "命中后把 +0x20 写成记录 +0xC"

**下一步**:
- 搜索 `FUN_006131F4` 的所有调用点, 过滤那些目标接近 +0x20/+0x38 的
- 检查同图传送函数 0x563CE1 (Ghidra RVA) 的完整反编译
- 可能写入在虚表回调中

### 5. 剩余 46 个运行时分派 sender

**问题**: 46 个发送函数的宿主通过运行时计算分派, 无静态调用者和引用。

**下一步**: 需要动态追踪或反编译器级数据流分析

### 6. 运行时 AES 轮询字节

**问题**: 保护器阻止带 NIC 的客户端物化, 无法捕获后登录内存。

**已验证替代**: 合成客户端用相同密钥成功通信, 协议栈完整。

**下一步**: 如需要实际字节布局, 需物理机安装或保护器绕过

## 突破方法论总结

1. **Ghidra unicode 标签搜索**: `[us]_(\w+)_([0-9a-f]+)` 模式提取 WZ 属性名
2. **加密调用链追踪**: FUN_006131F4(写) → FUN_00548806(读) → FUN_006A0545(解密)
3. **服务端 Java 源码对照**: 同一协议的 Java 实现比 x86 反编译更易读
4. **GLM-4V 视觉分析**: 截图 → 多模态 API → 文字描述 → 键鼠决策
5. **合成客户端验证**: 从 Python 直接构造协议包验证理解
